# Route Walker：エンドストーン巡回採掘の設計仕様

作成日: 2026-09-19。状態: **初期設計仕様。現在の作業ツリーには採掘機能の実装あり。全項目の実装適合・実機動作は未検証。**

ユーザー指定により、この既存巡回機能の名称は **Route Walker**。実装担当は別タスクの **5.6-sol** に変更。移動しない黒曜石採掘の **Obsidian Bot** は別機能とする。名称・キー・コマンドの互換性と新Botの実装指示は [OBSIDIAN_BOT_SOL_HANDOFF.ja.md](OBSIDIAN_BOT_SOL_HANDOFF.ja.md) を優先する。

追加要件「リニア旋回・初期速度120°/秒」「カメラのtick間補間」「チャット中のノード表示」「紫のリング・方向付き接続線」の原因と修正指示は [MINING_ROTATION_RENDER_FIX.ja.md](MINING_ROTATION_RENDER_FIX.ja.md) を参照する。速度・描画については追補仕様を優先する。前版の加減速調整案は廃止。バックグラウンド継続の要件は維持し、チャットを開いたときは採掘を停止してルート表示のみ継続する。

## 1. 目的と確認済みの要件

- ユーザーがコマンドで現在地にノードを登録する。
- 開始キーを押すと、登録順に `1 → 2 → … → N → 1` を繰り返す。同じキーで停止する。
- 視点を真下に向け、左クリック長押し相当の入力でエンドストーンを掘りながら走る。
- ユーザー確認: エンドストーンは同じ位置に再生し、ほぼ同じ高さで周回する。
- ユーザー指定: エンドストーン採掘可能なツールを持っている場合だけ開始を許可する。
- ユーザー指定: フォーカス喪失後も採掘・移動・照準を継続し、裏画面で周回できること。
- ユーザー申告: エンドストーンは1tickで掘れる。ただし破壊速度、再生時間、長押し時のブロック間隔は未実測。
- 説明は日本語。ゲーム内UI・通知・ログ・Controlsの表示は英語。
- このタスクのCodexが設計・レビュー、別タスクの5.6-solが実装する。

「1ブロックを1tickで壊せる」ことと「移動中に毎tick別のブロックを壊せる」ことを同一視しない。手動の左クリック長押しと同じ標準入力経路を使い、実ゲームで比較する。採掘ディレイの無効化、独自の破壊パケット、OS入力注入は行わない。

## 2. 推奨方式と採用基準

| 方式 | 効果 | コスト・難易度 | リスク・採用条件 |
| --- | --- | --- | --- |
| **推奨: 採掘専用の順序付きルート追従** | 登録した採掘経路を予測可能に巡回する | 中。小さな追従状態機械と入力管理を追加 | ノード間に壁や大きな段差がある場合は停止。ほぼ平坦な再生床という今回の条件に適合 |
| 次善: ノード間をA*で接続 | 障害物を迂回できる | 高。変化する床と再計画の調整が必要 | 迂回・短絡で意図した採掘帯を外れる。障害物のあるルートが必要になった場合に採用 |

初版の方針は以下。Hキー・ルート数などの未指定事項と、本文の暫定しきい値は設計上の既定値。数値は実機結果で調整できるよう定数または設定として分離する。バックグラウンド継続はユーザー指定の必須要件。

- 採掘用トグルは **H**、Controlsで変更可能。既存Gは戦闘用のまま。
- 保存ルートは初版では1本。名前付き複数ルートは別途拡張可能。
- フォーカス喪失後もゲームのtickが進む限り、採掘・移動・視点を継続する。Alt+Tabや他アプリ操作で停止しない。GUI表示、死亡、切断などの明示的な停止条件は維持する。
- 自動ジャンプ、ワープ、地形の自動迂回は行わず、通れる場所にユーザーがノードを置く。

## 3. 操作仕様

すべてFabricクライアントコマンドとして登録する。

| コマンド・操作 | 動作 |
| --- | --- |
| `/mining route add` | プレイヤーの現在の足元座標を末尾に登録し、番号・座標を表示 |
| `/mining route remove <index>` | 1始まりの指定ノードを削除して再採番 |
| `/mining route clear` | 保存ルートを消去 |
| `/mining route list` | ノードを登録順に表示。長い場合はページ表示または出力量制限 |
| `/mining status` | ON/OFF、ノード数、追従中の番号、周回数、直近の停止理由を表示 |
| `/mining stop` | 採掘マクロを停止し、所有入力を解除 |
| H / Controlsの `Toggle End Stone Mining` | 開始・停止 |

ノードは設置ブロックではなくクライアント側の座標データ。小数のX/Zと足元Yを保存し、勝手なブロック中心への丸めで経路を変えない。最後から最初への線分もルートに含む。最後に先頭と同じ座標を追加する必要はない。

最低2ノードを必要とする。2ノードは往復、3ノード以上は登録順の閉路となる。連続する同位置ノード、末尾と先頭の重複、非有限座標は登録・読込時に拒否する。交差ルートや非連続の同位置ノードは順序を保持して扱う。

開始はルート上のいずれかのノードの近くから行う。最寄りノードが水平2ブロック以内、高さ差0.75ブロック以内であることを暫定条件とする。同距離なら小さい番号を選ぶ。遠い場所から勝手にルートへ移動しない。

## 4. 追従・採掘の動作

1. ルート、ワールド、プレイヤー生存、GUI、戦闘との排他、手持ちアイテムを検証する。開始キーはゲームにフォーカスがあるときに受け付け、開始後はフォーカス・マウス捕捉を継続可否の条件にしない。
2. 手持ちがエンドストーンに対する標準の適正ツール判定を満たす場合だけ開始する。空の手や不適切なアイテムでは開始しない。26.2のAPIを確認し、レジストリIDや表示名だけの独自許可リストで代用しない。開始時の手持ちスロットとアイテム識別情報を記録する。
3. 最寄りノードへ合流する間は採掘を開始せず、視点を真下（pitch +90°）へ合わせる。
4. ノードへ到達したら次の番号へ進む。yawを次ノード方向へ向け、前進・スプリント・採掘を行う。
5. Nの次は1へ進む。停止条件が成立するか手動停止されるまで繰り返す。

ノード到達の水平許容値は暫定0.6ブロック。到達時にも高さがルートと整合することを確認する。現在位置の距離だけでなく、前tickからの実移動線分が到達範囲を通ったケースも扱い、高速移動時の行き過ぎによる往復振動を防ぐ。テレポート相当の不連続移動は通過扱いにせず停止する。

追従先の再選択は開始時だけ。走行中に毎tick最寄りノードを選び直さない。交差点でも登録順を守り、将来のノードを短絡しない。1tickで進めるノード数に上限を設け、重複・短距離ノードで無限ループしない。

周回数は合流完了を起点に全N区間を通過したときだけ増加する。途中ノードから開始して初めてN→1を通っただけでは1周と数えない。

旋回が必要な間は前進・スプリントを解除する。yawの最短角差を使い、±180°境界で大回りしない。yaw誤差15°以下で前進を再開する値を暫定とする。pitchは真下を保ち、yaw/pitchの書込み所有者を採掘用処理1つに限定する。スプリントはvanillaの条件が成立する範囲で要求し、速度や空腹条件を改変しない。

自動採掘は真下の現在の標準照準先が `Blocks.END_STONE` のときだけ許可する。空気・他ブロック・エンティティでは自動Attackを解除する。再生待ちや採掘帯の隙間では走行条件が満たされれば移動を続け、エンドストーンに照準が戻れば再保持する。各ブロックの破壊待ちでルート進行を固定しない。

真下への回転前の古い `hitResult` を使って別のブロックを掘らない。26.2で照準更新、hotbar入力、Attack消費、継続採掘が実行される順序を調べ、実際の採掘消費時に条件が成立するようにする。

ツール判定は開始時と採掘入力適用前に行う。標準の適正ツール判定で分かるのはクライアント側の適性であり、サーバー独自の採掘速度・採掘権限・カスタムアイテム能力までは保証しない。1tick採掘可能かどうかを標準判定から断定しない。実機で有効なカスタムツールが標準判定を通らない場合は、その差を記録して登録方式等を別途検討し、無条件許可へ黙って緩めない。

## 5. 停止・再生床への対応

- 同じトグルキー、`/mining stop`、GUI表示、死亡、切断、ワールド・ディメンション変更、クライアント終了で停止。フォーカス喪失は停止条件にしない。
- 手持ちスロット変更、アイテム識別変更、空の手・不適切なツールになった場合も停止。通常の耐久値減少だけで持ち替え扱いにしない。非フォーカス中は物理キー状態を参照して自動入力を解除しない。
- 地形で前進不能、ルートから大きく逸脱、想定外の落下、不連続移動、未ロードの進行先を検知したら停止する。再接続やGUIを閉じただけで自動再開しない。
- 停止は採掘側が所有した入力だけを解除し、フォーカス復帰後のユーザーの物理押下を壊さない。非フォーカス中の古いGLFW状態を物理入力として採用しない。
- 再生直前の空気を見ただけで即マクロOFFにしない。採掘可否と移動可否は別に評価する。
- 前方の身体が通れる空間と支持床を実際のcollisionで確認する。危険な床の欠損では入力を一時解除し、短時間の再生待ちが可能な状態にする。待機中も死亡・GUI等は即停止条件。
- 再生待ちの上限は暫定40tick。範囲外の落下や障害物は待機を延長せず停止。待機中に前進・Attackを残さない。
- ルートの高さは到達・逸脱の検証用に保持し、X/Zだけ合えば何階下でも追従を続ける実装にしない。高さ許容値と再生待ちの条件は実測で調整する。

スタックは「前進を要求した区間で、水平位置または区間方向の進捗が不足」を基準に検出する。停止中の旋回・再生待ちは除外し、重力による上下移動だけを正常な進捗と数えない。暫定として40tickで水平0.25ブロック未満を停止候補とする。時間計測はtick数または単調時計を使う。

### バックグラウンド継続

- 採掘・移動・yaw/pitch更新・ノード通過判定をclient tickを基準に進める。render callbackだけで角度・照準・経路進行を更新する構成にしない。描画を減らしても内部の旋回が止まらないようにする。
- 標準の照準更新が描画に依存していないか26.2で確認する。必要なら採掘処理の前に標準のpick/raycast経路を適切な時点で更新し、採掘可否の判定とvanillaが実際に消費する照準先を一致させる。描画が止まった後の古い `hitResult` で掘り続けない。
- フォーカス喪失時やvanillaの入力リセット後も、そのtickで許可された自動入力だけを再適用する。旋回・再生待ち・停止中まで前進やAttackを強制しない。
- 他アプリでのキー・マウス操作をマクロ操作と解釈しない。開始・停止キーはフォーカス中にだけ受け付け、非フォーカス中の残留clickを復帰後に実行しない。復帰後に実際に押したHは、そのtickの採掘・移動入力を消費する前に停止へ反映する。
- 採掘セッションの現在の有効条件を確認し、有効な間だけフォーカス喪失による自動ポーズを抑止する。再生待ち等でAttackが一時解除されていても、有効なセッションなら待機処理を継続する。OFF・GUI・死亡・切断では抑止しない。
- 最小化、非アクティブ時のFPS制限、他MODによるtick抑制はそれぞれ実機で確認する。tickそのものが停止する環境では進行できないため、Alt+Tabの成功だけで最小化時や他MOD併用時まで動作確認済みと報告しない。

## 6. 既存コードとの統合で守ること

2026-09-19の読取確認: `codex/frozen-scythe` / HEAD `51c6f6e`。Frozen Scytheの非フォーカス保持修正は未コミット。作業開始時に再度差分を確認し、既存変更を保持する。commit・push・reset・checkoutによる上書きを勝手に行わない。

- `DragsimMacroClient.java`: G/Scythe HoldはSTART tick、戦闘・移動・回転はEND tick、回転にはrender callbackもある。採掘中はこれらが採掘入力・回転を上書きしないよう実行を調停する。
- `MacroController.java`: 現在は戦闘側の状態管理。`CombatMode`にMININGを足すだけで戦闘処理へ流す実装は避ける。採掘は独立したControllerとする。
- 排他は共通の実行時状態で保証する。戦闘ON中の採掘開始、採掘ON中の戦闘開始は理由付きで拒否する。キーだけでなくGUI・コマンドからの開始も対象とする。
- 戦闘のAttack/Approach/Rotationの保存設定を一時停止のために書き換えない。採掘停止後も戦闘は自動開始しない。
- 採掘開始時に戦闘側の残った移動・Use・照準objective等を一度整理してから入力所有権を取得する。停止済みの戦闘処理が毎tick解除処理を呼び、採掘の入力を消す構造を避ける。
- `RotationController.java`はtickとrenderの経路を持つ。両方の競合を止める。戦闘ターゲットがないことだけを排他の根拠にしない。
- `PathFollower.java`はノード省略、先読み、ジャンプ、戦闘設定との結合がある。今回のルートを丸ごと渡して使わない。純粋な角度・線分距離計算は再利用可能。
- `ScytheHoldSession.java`の保持・再適用・物理入力との共存方針を採掘入力でも参考にする。既存Useの状態や所有フラグをAttackに共用しない。
- 入力は標準KeyMapping経路を基本にする。`keyAttack`、`keyUp`、`keySprint`を一箇所で管理し、保持中は必要に応じて再適用する。clickキューの連打、直接の破壊APIとの二重呼出し、独自パケットを加えない。
- `ScytheHoldMinecraftMixin.java`はすでに存在する。採掘でも非フォーカス時の自動ポーズ抑止が必要なら、26.2の実行順を根拠に同じhookへ安全に統合するか、採掘用hookを分離する。既存の右クリック保持hookを採掘の正しいタイミングと決めつけない。
- 採掘中だけ `pauseIfInactive` の自動ポーズを抑止する。保存設定 `pauseOnLostFocus` を書き換えず、Escメニュー等の手動GUIは停止条件のままにする。
- 非フォーカス中は物理マウス・キーボード状態を参照せず、自動入力の保持・解除を決める。`ScytheHoldSession` の方式を参考に採掘専用の所有状態を管理する。停止時の物理押下保全はフォーカス中のみ適用し、非フォーカス中の古い押下状態で自動入力の解除を妨げない。
- `LifecycleSafety.java`、`ScreenEvents.BEFORE_INIT`、クライアント終了時の解除に採掘も接続する。
- key categoryは既存の共有インスタンスを使い、同じIDで再登録しない。

クラス分割の目安: `MiningController`（MC接続・状態管理）、`MiningRouteFollower`（MC非依存の順序・通過判定）、`MiningInputSession`（入力所有）、`MiningRouteStore`（永続化）、`MiningCommand`。必要以上の全体リファクタリングはしない。

## 7. 保存・通知

- ルートはFabricのconfigディレクトリ配下 `dragsimmacro-mining.json` に保存。既存戦闘configと分ける。
- schemaVersion、ノード列、ワールド識別情報、dimensionを保存。ノード追加・削除・消去が成功したときに保存し、tick毎に書かない。
- サーバー接続先とdimension（シングルプレイはセーブ識別情報）を検証する。同一接続先・dimensionでもサーバー内の別エリアまでは識別できない場合があるため、開始地点との距離チェックを併用する。
- 実行ON/OFF、周回数、入力所有状態、現在ノードは永続化せず、ゲーム再起動時は必ずOFF。
- ノード数上限を設ける（暫定512）。無効な数値、過大データ、未知のschemaVersion、壊れたJSONを検証する。
- 読込失敗時に空ルートを保存して原本を上書きしない。保存は一時ファイルからの置換を使い、失敗した場合は成功通知を出さず、前の有効状態を維持する。
- 通知例: `[DragSim] Mining ON — 8 nodes`、`[DragSim] Mining OFF — GUI opened`、`[DragSim] Mining cannot start — combat macro is active`。
- ログと通知は開始・停止・エラーなどの状態変化時に記録する。tick毎の同期ファイル書込みや採掘毎の通知は避ける。

## 8. 受入条件・検証

MC非依存ロジックの単体テスト:

- 2ノード往復、複数ノードの閉路、途中から開始した周回数、交差点での順序保持。
- 到達範囲をtick間に通り抜ける場合、境界付近、±180°の旋回、重複・無効ノード。
- 上下の違う同じX/Zを誤到達にしない。不連続移動で一度にノードを進めない。
- 床の一時欠損・再生・待機期限、水平スタック、停止中の誤判定防止。
- すべての停止経路で所有入力を解除。vanilla入力リセット後の再保持、非フォーカス中の継続、フォーカス復帰後の物理押下保全。
- 描画callbackなしでも、tickによって採掘用の回転・ノード進行が更新されること。非フォーカス中は物理入力を読まず、停止時は古い物理押下状態にかかわらず所有入力を解除すること。
- 適正ツール、空の手、不適切なアイテム、持ち替え、ツール消失に対する開始・停止判定。純粋ロジックでは適性判定結果を入力とし、実際の26.2 API判定は実機でも確認。
- 戦闘/採掘の同時開始を防ぎ、無効な開始操作が現在の実行者の入力を解除しない。
- JSON往復、壊れたデータを上書きしないこと、保存失敗、ワールド不一致。

実ゲームで別途確認する項目:

1. 新JARで起動。追加・変更したMixinがある場合は適用と例外の有無を確認。
2. 4ノードの平坦な再生床で3周以上、順序・真下視点・移動・採掘・周回数を確認。
3. 急角度、2ノード折返し、高速移動、開始位置からの合流で振動・短絡を確認。
